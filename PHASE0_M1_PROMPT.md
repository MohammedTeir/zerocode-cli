## Part A — Phase 0 gates (report only, no product code changes)

1. **Baseline branch.** Confirm the tag exists (`git tag --list 'v2.*'`, `git rev-parse v2.3.0^{commit}`). Create `zerocode/baseline` from that exact tag. Record the commit hash and how many commits it is behind `upstream/dev`.
2. **Evidence on the tag.** On `zerocode/baseline`, run these as separate commands and save full output under `reports/baseline/` (do not commit the logs):
   - `bun install --frozen-lockfile`
   - `bun run lint`
   - `bun run typecheck`
   - `bun run --cwd packages/cli build`
   - `bun run --cwd packages/core test`
   - `bun run --cwd packages/cli test`
3. **Classify every failing test** as environment, upstream bug, or flaky, with proof. For suspected environment causes, check `git --version`, `git config user.name`, `git config user.email`, and `init.defaultBranch`, then rerun the failing files with those set in a temporary `HOME`. Report failure counts before and after. Failures in VCS, snapshot, shell-parse, and MCP session-expiry tests need a clear explanation.
4. **Build dependency closure.** The CLI build bundles a web app (the PWA precache step). Inspect the build scripts and imports and produce a table: package, needed by the CLI build or TUI (yes/no), why. This decides what the scope cut can safely remove.
5. **Config-discovery audit.** List every config root the CLI reads (`.opencode`, `.claude`, `.agents`, global and managed paths), with the file and line that reads it. Propose which become opt-in.
6. **Egress audit by command.** For each CLI command (`upgrade`, `uninstall`, `acp`, `api`, `debug`, `auth`, `mcp`, `plugin`, `models`, `stats`, `mini`, `run`, `pair`, `reload`, `session`, `service`, `serve`, and the default TUI start), find the network calls statically and, where possible, run it with networking disabled and record what fails or retries.
7. **Container runtime.** Report whether Docker or Podman is installed and usable.
8. **Write `docs/phase0-gates.md`** with the results above and a short list of decisions I need to make (rename policy, scope cut, config roots, anything else you found).

Then **stop** and wait for my approval.

## Part B — M1: rename, branding, license (only after approval)

Branch `m1/rename-branding-license` from the approved baseline. M1 changes names, notices, and branding. It does not change runtime behavior except the explicit migration command; privacy and network lockdown is M2.

### B1. License and notices

- Keep the root `LICENSE` verbatim and add a ZeroCode copyright line beside it.
- Add `NOTICE`: ZeroCode is based on OpenCode (link to upstream), and is not affiliated with or endorsed by the OpenCode team.
- Add `THIRD_PARTY_NOTICES.md`, generated by a committed script (for example `script/generate-third-party-notices.ts`) from the real dependency tree. Flag any dependency that is not permissive.
- Review the extra license surfaces from the Phase 0 report (`packages/http-recorder`, `packages/process-daemon` and its bundled Ghostty license, `packages/ui`, the vendored eslint-stylistic code, the test262 and WPT license files, `packages/core/src/image/notice.ts`, the Figma plugin notice, and the `.github/release` dependency trees). For each, decide keep (with notice) or remove, and record why.

### B2. Rename (per the approved rename policy)

- Binary: `zerocode`. Remove the `opencode2` alias.
- Published package name, repository links, and package metadata.
- Environment variables: `OPENCODE_*` to `ZEROCODE_*`.
- Config: `.zerocode/`, `zerocode.json` and `zerocode.jsonc`, `~/.config/zerocode/`, and the matching state, cache, data, and log paths.
- All user-visible text: help output, TUI strings, error messages, built-in agent, skill, and command text, docs.
- URLs that point to OpenCode-owned domains: remove or replace with ZeroCode-owned or placeholder values. Do not invent domains.
- Do the renames with a scripted, reviewable codemod, not hand edits, and commit the codemod script or its description.

### B3. Explicit migration

- Add `zerocode migrate-opencode`. It defaults to a dry run that lists what would be copied from `.opencode/`, `opencode.json*`, and the global OpenCode config. It copies only after I confirm.
- ZeroCode never reads or modifies OpenCode (or `.claude`, `.agents`) config on its own.
- Tests: a fixture with only an `.opencode/` folder proves ZeroCode ignores it; a second test proves the migration dry run changes nothing.

### B4. Branding

- Remove OpenCode logos, wordmarks, icons, and brand assets from the retained packages. Use a plain text ZeroCode wordmark in the TUI until real branding exists.
- Add the non-affiliation statement to the README and `NOTICE`.

### B5. Scope cut (only what I approved)

- Remove or isolate only the packages and services I approved after Part A. Prove with a build and a search that nothing retained imports or contacts the removed ones.

### B6. Docs

- Rewrite `README.md` minimally: only behavior you have verified.
- Add `docs/upstream-sync.md` (patch inventory with reason, file, risk, and merge strategy; sync procedure) and `docs/migration-from-opencode.md`.
- Update `docs/architecture.md` to match the new names.

## M1 acceptance criteria

Show real output for each:

1. Install, lint, typecheck, and build pass.
2. The failing tests are exactly the baseline set from Part A, with no new failures.
3. `zerocode --version` and `zerocode --help` work and show no OpenCode names.
4. `zerocode` starts the TUI. Verify with a pseudo-terminal smoke test, or say it could not be verified.
5. A case-insensitive search for `opencode` across retained code shows only the checked-in allowlist (for example `LICENSE`, `NOTICE`, migration code and docs, `docs/upstream-sync.md`, and internal scopes if the policy keeps them). CI fails on any other hit.
6. No `OPENCODE_` environment variable remains.
7. The tests from B3 pass.
